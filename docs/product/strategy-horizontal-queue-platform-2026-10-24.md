# Quego — กลยุทธ์ "เบอร์ 1 ระบบคิวทุกอุตสาหกรรม" (ฉบับ 2026-10-24)

> โจทย์จากเจ้าของ: ฟีเจอร์ที่เสนอใน [product-gap-and-opportunity-review-2026-10-24.md](product-gap-and-opportunity-review-2026-10-24.md)
> ไม่ช่วยให้ร้านสมัคร/ใช้จริง และไม่ควรจำกัดแค่ร้านตัดผม ต้องรองรับทุกอุตสาหกรรมที่จองคิวได้
> เอกสารนี้ตอบ 6 คำถาม: (1) จะเป็นเบอร์ 1 ทุกอุตสาหกรรมได้อย่างไร (2) ผู้ใช้ได้อะไร (3) ร้านต่อยอดธุรกิจได้อย่างไร
> (4) ผู้พัฒนาระบบได้อะไร (5) ทำไมทุกคนจะมาใช้ (6) จุดแข็งที่ต่างจากคู่แข่งอยู่ตรงไหน
>
> ข้อเท็จจริงเรื่องคู่แข่ง/ตลาดอ้างอิงจาก review ฉบับเดียวกัน (เข้าถึง 2026-10-24) ส่วนที่เป็นข้อเสนอระบุเป็น **[REC]**

## 0. คำตอบสั้น

**"ระบบจอง" (appointment software) เป็นสนามที่ชนะด้วยฟีเจอร์ไม่ได้แล้ว** ทั่วโลกมี Fresha/Booksy/Square/SimplyBook ในไทยมี ≥ 8 รายที่ฟรี และ LINE เองก็พร้อมลงมาเล่นเมื่อไหร่ก็ได้ การเป็น "เบอร์ 1 ทุกอุตสาหกรรม" ด้วยการไล่ทำฟีเจอร์ให้ครบทุก vertical คือทางที่แพ้แน่ เพราะทุก vertical มีเจ้าถิ่นที่ลึกกว่า (คลินิกมี HIS, ร้านอาหารมี POS, โรงพยาบาลมี QueQ)

**สนามที่ยังไม่มีเบอร์ 1 ในไทยคือ "คิว" ในฐานะโครงสร้างพื้นฐานฝั่งผู้บริโภค** — คนไทยคนหนึ่งต่อคิวสัปดาห์ละหลายครั้ง (หมอ, ธนาคาร, ราชการ, ร้านอาหาร, ตัดผม, ล้างรถ, ติวเตอร์, วัคซีน, ซ่อมมือถือ) แต่ทุกคิวอยู่คนละระบบ คนละ OA คนละแอป ไม่มีใครเป็น "ที่เดียวที่รู้ว่าฉันต้องรออีกเท่าไหร่" QueQ เคยพยายามแต่ขายฮาร์ดแวร์ให้องค์กรใหญ่และบังคับโหลดแอป จึงไม่เคยถึงร้านเล็ก 120,000 ร้าน

**ข้อเสนอ [REC]: เปลี่ยนนิยามผลิตภัณฑ์จาก "ระบบจองคิวร้านความงาม" เป็น "Queue layer ของประเทศไทย" — ฝั่งร้านได้เครื่องยนต์คิว+จองที่ตั้งค่าได้ทุกธุรกิจ ฟรี ไม่ต้องมีแอป ไม่ต้องมี LINE OA · ฝั่งผู้บริโภคได้ตัวตนเดียว (เบอร์โทร) ที่เห็นทุกคิวในชีวิตที่เดียว · ฝั่งผู้พัฒนา/แพลตฟอร์มอื่นได้ API ให้ฝังคิวเข้าระบบตัวเอง** ชนะด้วย 3 อย่างที่คู่แข่งไทยไม่มีรายใดมีพร้อมกัน: engine ที่รวม walk-in กับนัดหมายในลำดับเดียวแบบ race-safe · ต้นทุน LINE เป็นของเรา · ตัวตนผู้บริโภคข้ามร้าน (network effect)

## 1. ทำไม "ทุกอุตสาหกรรม" ถึงเป็นไปได้ — เพราะ engine เราเป็นกลางอยู่แล้ว

สิ่งที่โค้ดปัจจุบันไม่ได้ผูกกับร้านตัดผมเลย (ยืนยันใน `src/`):

| ความสามารถ | ร้านตัดผมใช้เป็น | อุตสาหกรรมอื่นใช้เป็น |
|---|---|---|
| `shop_services` (ชื่อ, ระยะเวลา, ราคา) | ตัดผม 40 นาที | ตรวจฟัน 30 นาที · ล้างรถ 60 นาที · ติว 90 นาที · นวด 120 นาที |
| `shop_staff` + staff↔service | ช่างแต่ละคน | หมอแต่ละคน · ช่องบริการ · เตียง · ลิฟต์ยก · ติวเตอร์ |
| slot-math + GiST overlap ต่อเลน | ช่างไม่ชนกัน | ห้องตรวจไม่ชนกัน · โต๊ะไม่ชนกัน |
| walk-in QR → คิวที่ช่องว่างเร็วสุด | ลูกค้าเดินเข้าร้าน | คนไข้ walk-in · ลูกค้าธนาคาร · ผู้มาติดต่อราชการ |
| live queue "อีก N คิว" + now-serving display | จอหน้าร้าน | จอหน้าห้องตรวจ · จอหน้าเคาน์เตอร์ |
| waitlist + เสนอคิวว่างทาง LINE | คิวเต็ม | คลินิกเต็ม · คอร์สเต็ม |
| CRM ตามเบอร์ + โน้ต | ลูกค้าประจำ | ประวัติคนไข้แบบเบา · ประวัติรถ |
| categories + `category_service_presets` | หมวดความงาม | **หมวดใดก็ได้ที่ admin สร้าง** — โครงรองรับแล้ว |

**สิ่งที่ยังผูกกับความงาม/ร้านเล็ก และต้องปลดก่อนขยาย [CODE]**: copy หน้า landing และชื่อหมวด · ข้อจำกัด `duration % 10 = 0, ≥10 นาที` · เวลาเปิดข้ามเที่ยงคืนไม่ได้ · ไม่มี capacity > 1 ต่อ slot (คลาส/กลุ่ม) · ไม่มี "ทรัพยากร" ที่ไม่ใช่คน (ห้อง, โต๊ะ, เครื่อง) · ไม่มีโหมด "คิวอย่างเดียวไม่รับจอง" (ธนาคาร/ราชการ) · ไม่มีหลายสาขา/หลาย role · ไม่มี API/webhook ให้ระบบอื่นเรียก

→ **ระยะทางจาก "ร้านตัดผม" ไป "ทุกธุรกิจ" คือการ generalize โมเดลข้อมูล 5 จุด ไม่ใช่สร้างใหม่** (ดู §6)

## 2. ผู้ใช้ (ผู้บริโภค) ได้อะไร — "ทุกคิวในชีวิต ที่เดียว ไม่ต้องโหลดแอป"

ความเจ็บที่ไม่ขึ้นกับอุตสาหกรรม (จากเสียงผู้ใช้ใน review): **"ไม่รู้ต้องรออีกเท่าไหร่"**, **"จองแล้วยังต้องไปนั่งรอ"**, **"ทักไปแล้วร้านไม่ตอบ"**, **"แต่ละที่ให้แอดไลน์คนละอัน/โหลดแอปคนละตัว"**

| ผู้ใช้ได้ | ทำไมคู่แข่งให้ไม่ได้ |
|---|---|
| **ตัวตนเดียว** (เบอร์โทร + LINE ครั้งเดียว) ใช้ได้ทุกร้านบน Quego ไม่ต้องกรอกซ้ำ ไม่ต้องแอด OA ทุกร้าน | คู่แข่งผูกกับ OA ของร้าน → ทุกร้านคือ silo ใหม่ |
| **เห็นทุกคิว/นัดในที่เดียว** `/me/bookings` ข้ามร้านข้ามประเภท พร้อมเตือน | ไม่มีใครรวมได้เพราะไม่มีฝั่งผู้บริโภคร่วม |
| **รู้ว่าอีกกี่คิว อีกกี่นาที แบบสด** ออกไปทำธุระได้ | QueQ ทำแต่บังคับแอป+อยู่ใกล้ 2 กม.; booking tools ไม่มีคิวสด |
| **ไม่ต้องโหลดแอป** เว็บ + LINE พอ (iOS 26 ทำให้เว็บที่เพิ่มลงหน้าจอเป็นแอปโดยอัตโนมัติ) | QueQ/GoWabi ต้องโหลดแอป |
| **ค้นหา "ใกล้ฉัน" ข้ามหมวด** + ว่างเร็วสุด | รายอื่นเป็น tool ของร้าน ไม่มี discovery; GoWabi มีแต่เฉพาะความงาม + deal |

**[REC] คำสัญญาฝั่งผู้ใช้ที่ควรยึด**: "ไม่ต้องรอเก้อ" (มีอยู่แล้ว) ขยายเป็น **"รู้คิวทุกที่ ก่อนออกจากบ้าน"**

## 3. ร้าน/ธุรกิจต่อยอดได้อย่างไร — จาก "รับคิว" เป็น "ดำเนินธุรกิจบนข้อมูลคิว"

ธุรกิจที่ใช้คิวทุกประเภทมีสมการเดียวกัน: **กำลังการผลิต (คน/ห้อง × ชั่วโมงเปิด) − คิวหลุด − เวลาว่าง = รายได้** Quego ถือข้อมูลทั้ง 3 ตัว

| ชั้น | ร้านได้ | สถานะ |
|---|---|---|
| **1. รับคิวให้ถูกต้อง** | ไม่ชน ไม่จดผิด walk-in กับจองอยู่ลำดับเดียว | ✅ มีแล้ว |
| **2. ลดคิวหลุด** | เตือนอัตโนมัติ, นับ no-show, ความน่าเชื่อถือต่อเบอร์, มัดจำแบบมีเงื่อนไข | ❌ (N1/N2/X2 ใน review) |
| **3. เติมเวลาว่าง** | waitlist เติมช่องที่ยกเลิก, "ว่างเร็วสุด" ดึงลูกค้าใหม่, ราคา off-peak (เทรนด์ Fresha 2026) | ⚠️ waitlist มี, ที่เหลือไม่มี |
| **4. รู้ตัวเลขธุรกิจ** | utilization ต่อคน/ห้อง, ชั่วโมงพีค, รายได้ต่อบริการ, กำไรสุทธิหลังค่าใช้จ่าย | ✅ มีแล้ว (รายเดียวในตลาดที่มีกำไรสุทธิ) |
| **5. ลูกค้าเป็นของร้าน** | CRM ตามเบอร์, export ได้, ไม่เก็บคอมมิชชัน | ⚠️ CRM มี, export ไม่มี |
| **6. ขยาย** | หลายสาขา, หลาย role, API ต่อ POS/บัญชี | ❌ |

**[REC] ข้อความขายร้านที่ใช้ได้ทุกอุตสาหกรรม**: *"ตั้งคิวร้านคุณใน 10 นาที ฟรี ไม่ต้องมี LINE OA ไม่ต้องซื้อจอ ลูกค้าไม่ต้องโหลดแอป — และข้อมูลลูกค้าเป็นของคุณ"*
ทุกประโยคในนี้เป็นจริงในโค้ดวันนี้ ยกเว้น "ข้อมูลเป็นของคุณ" ที่ต้องมี export ก่อน

## 4. ผู้พัฒนาระบบ (Quego) ได้อะไร — 4 ทางรายได้ที่ไม่ขัดกับ "ฟรีสำหรับร้าน"

ตลาดไทยพิสูจน์แล้วว่า **ร้านเล็กไม่จ่าย** (ฟรีถาวรมี ≥ 5 ราย, กำไรร้าน ~19,000 บาท/เดือน) และ **ไม่ชอบคอมมิชชัน** (กขค. สั่ง freeze ค่าคอม; LINE เองบอกว่า SME หนีค่าธรรมเนียม) ดังนั้น:

| ทาง | ใครจ่าย | เมื่อไหร่ | เหตุผลที่ยั่งยืน |
|---|---|---|---|
| **A. Free forever สำหรับร้านเดี่ยว** | ไม่มีใคร | ตลอด | สร้างฝั่ง supply ให้ network effect เกิด; ต้นทุน LINE ~1,280–1,780 บาท/เดือน ครอบคลุม 3,750–8,750 การจอง |
| **B. Pro/Business สำหรับธุรกิจที่มีหลายสาขา/หลายคน** | คลินิก, เชน, ศูนย์บริการ | เมื่อมี multi-branch + roles | ลูกค้ากลุ่มนี้จ่าย 990–4,999/เดือนให้คู่แข่งอยู่แล้ว (QueueBooking, BeTask) และต้องการ audit/roles/report ที่ร้านเดี่ยวไม่ต้องการ |
| **C. Platform API / white-label** | POS, LINE OA vendor, แอปสถานพยาบาล, แพลตฟอร์มอื่น | เมื่อมี API keys + webhooks | ทุกรายอยากมี "จองคิว" แต่ไม่อยากสร้าง engine race-safe เอง; LINE MAN Wongnai เพิ่งซื้อ JERA Cloud (POS คลินิก/สปา 1,700 สาขา) แต่ยังไม่มี booking → เราเป็น engine ให้ได้ |
| **D. ฝั่งผู้บริโภค (ระยะยาว)** | ร้านที่อยาก "โผล่ก่อน" ใน discovery, หรือ consumer premium | เมื่อ discovery มี traffic จริง | GoWabi มี 1M ผู้ใช้/เดือนจาก organic — ค่าโฆษณาตำแหน่ง ไม่ใช่คอมมิชชันต่อการจอง |

**สิ่งที่ห้ามทำ**: คอมมิชชันต่อการจอง (ขัดกับ positioning และกฎหมายกำลังมา), gate reminder/ข้อความ (คู่แข่งทำหมด เราคือข้อต่าง), card-on-file

**ผลประโยชน์ที่ไม่ใช่เงิน**: ข้อมูลคิวข้ามอุตสาหกรรมทั้งประเทศ = สินทรัพย์ที่ไม่มีใครมี (เวลารอเฉลี่ยต่อประเภทธุรกิจ, no-show rate ไทยจริง, พีคตามจังหวัด) ใช้ทำ content, ขาย insight, หรือเป็นเหตุผลที่ LINE/ธนาคาร/แพลตฟอร์มอยากซื้อ

## 5. ทำไมทุกคนจะมาใช้ — 3 เสาที่คู่แข่งไทยไม่มีรายใดมีพร้อมกัน

จาก feature matrix ใน review (MeQueue, QueueBooking, QueueD, BookQ, NudNow, BeTask, Bookio, FoxConnect, ZERVA, Loga, Q Natural, GoWabi, QueQ, Fresha):

| เสา | เรา | คู่แข่ง | ทำไมพูดตามยาก |
|---|---|---|---|
| **1. Hybrid engine: walk-in + นัดหมายในลำดับเดียว, race-safe, คิวสดต่อเลน** | ✅ | booking tools = นัดหมายอย่างเดียว · QueQ/Q Natural = ticket อย่างเดียว (ฮาร์ดแวร์) | ต้องออกแบบ data model ใหม่ (GiST + lane) ไม่ใช่เพิ่มปุ่ม |
| **2. ร้านไม่ต้องมี LINE OA, ไม่จ่ายค่าข้อความ, ลูกค้าไม่ต้องแอดทุกร้าน** | ✅ | ทุกราย (8/8) วิ่งบน OA ของร้าน ร้านจ่าย quota เอง | เป็น cost-structure ที่ vendor ซึ่งขายรายเดือนไม่อยากแบก และเป็น architecture ที่เปลี่ยนทีหลังยาก |
| **3. ตัวตนผู้บริโภคข้ามร้าน + discovery ข้ามหมวด** | ✅ โครง (เบอร์เป็น identity, `/me`, near-me) | ไม่มีใครมีฝั่งผู้บริโภคร่วม ยกเว้น GoWabi (เฉพาะความงาม) และ QueQ (ต้องแอป) | ต้องการ supply ข้ามหมวดก่อน = เหตุผลที่ต้องไป horizontal |

เสา 1+2 ทำให้ **ร้านสมัคร** (ถูกกว่า ง่ายกว่า รองรับหน้าร้านจริง) · เสา 3 ทำให้ **ร้านอยู่ต่อ** (ลูกค้าใหม่มาจาก network) และทำให้ **ผู้ใช้กลับมา** (คิวทุกที่อยู่ที่เดียว)

**ความจริงที่ต้องยอมรับ**: เสา 3 วันนี้ยังเป็นศูนย์เพราะไม่มี supply — มันคือ *ผล* ของการชนะ ไม่ใช่ *เหตุ* ช่วง 12 เดือนแรกชนะด้วยเสา 1+2 เท่านั้น

## 6. จะไปถึง "เบอร์ 1" อย่างไร — ลำดับที่ถูก

### 6.1 นิยาม "เบอร์ 1" ให้วัดได้ [REC]
ไม่ใช่ "ฟีเจอร์เยอะสุด" แต่คือ **จำนวนคิวที่ถูกรับผ่าน Quego ต่อวันทั่วประเทศ** (metric เดียวที่สะท้อนทั้งร้านและผู้ใช้) · milestone: 1,000 คิว/วัน → 10,000 → 100,000 (QueQ ที่พีคอ้าง ~หลักแสน/วันในองค์กรใหญ่ [ไม่ยืนยัน])

### 6.2 ทำ engine ให้เป็นกลางจริง (ไตรมาส 1) — 5 การ generalize
| # | จาก | เป็น | ปลดล็อก |
|---|---|---|---|
| G1 | `shop_staff` = คน | **resource** (คน / ห้อง / โต๊ะ / เครื่อง / ช่อง) + `capacity` ต่อ slot | คลินิก, ร้านอาหาร, คลาส, ล้างรถ, ติวกลุ่ม |
| G2 | โหมดเดียว (นัดหมาย + walk-in) | **3 โหมดต่อร้าน**: นัดหมายอย่างเดียว / คิวอย่างเดียว (ticket ไม่ระบุเวลา) / hybrid | ธนาคาร ราชการ โรงพยาบาล ร้านอาหาร |
| G3 | duration 10–480 นาที step 10, เวลาเปิดไม่ข้ามวัน | duration ยืดหยุ่น (5 นาที–หลายวัน), ข้ามเที่ยงคืน, buffer | ซ่อม/ฝากรถหลายวัน, ร้านเปิดดึก, สปา |
| G4 | 1 ร้าน 1 เจ้าของ | **สาขา + role** (เจ้าของ / ผู้จัดการ / พนักงานหน้าเคาน์เตอร์ / ผู้ให้บริการ) | เชน, คลินิก, ศูนย์บริการ |
| G5 | หมวดความงาม + presets | **industry templates**: ตั้งร้านด้วยเทมเพลต (บริการ, resource, โหมด, copy) ใน 10 นาที | ทุกอุตสาหกรรม onboard เองได้ |

ทั้ง 5 ข้อทำบน schema เดิมได้ (เพิ่มตาราง/คอลัมน์ ไม่ต้องรื้อ GiST) — risk หลักคือ UI ร้านต้องเปลี่ยนจาก "ช่าง" เป็นคำกลาง

### 6.3 ทำให้ "ฝังได้ทุกที่" (ไตรมาส 1–2) — เพราะร้านอยู่ที่ไหน คิวต้องไปที่นั่น
- ลิงก์/QR/rich menu (มีแล้ว) + **widget ฝังเว็บ** + **ปุ่มจองบน Google Business Profile** + **Reserve with Google เมื่อยืนยันไทย**
- **Public API + webhooks + API keys** (ทาง C ของรายได้): สร้างคิว, อ่านสถานะ, รับ event — ให้ POS/OA vendor/แอปอื่นใช้ engine เรา
- **LINE MINI App (Unverified) เป็นทางเข้า** หลังวัดว่า rich menu ไม่พอ (เงื่อนไขใน review §2.1)

### 6.4 เลือก beachhead 3 vertical ที่ engine เดียวกันรองรับ ไม่ใช่ "ทุกอุตสาหกรรมพร้อมกัน" [REC]
"ทุกอุตสาหกรรม" เป็น *สถาปัตยกรรม* ไม่ใช่ *แผนการตลาด* — ขายทีละกลุ่มที่ (ก) ไม่มีเจ้าถิ่นลึก (ข) มี walk-in + นัดหมายปนกัน (ค) เจ็บเรื่อง no-show/รอนาน (ง) เข้าถึงได้ผ่านกลุ่ม LINE/Facebook เดียวกัน

| ลำดับ | กลุ่ม | ทำไม | สิ่งที่ต้องมีเพิ่ม |
|---|---|---|---|
| 1 | **ความงาม/wellness** (ที่ทำอยู่) + **นวด/สปา 16,600 ร้าน** | engine ตรง, ฐาน demo มีแล้ว, นวดต้องการ "เลือกหมอ/เพศ/ห้อง" ซึ่งคือ G1 | G1 (ห้อง/เตียง), G3 (เปิดดึก), ภาษาอังกฤษสำหรับนักท่องเที่ยว |
| 2 | **คลินิกเล็ก: ทันตกรรม, สัตวแพทย์, กายภาพ, ความงาม** | จ่ายได้ (ทาง B), no-show เจ็บมาก, HIS ใหญ่ไม่ลงมาถึงคลินิก 1–3 หมอ, JERA Cloud ถูกซื้อไปแล้วแต่ยังไม่มี booking | G1 (ห้องตรวจ), G4 (role หน้าเคาน์เตอร์), privacy บนจอ (เลขคิวไม่ใช่ชื่อ), PDPA export |
| 3 | **บริการรถ: ล้าง/ดีเทล/ซ่อม/ยาง** | ปนกันระหว่าง walk-in กับนัด, บริการยาว, ไม่มีเจ้าถิ่นไทย | G1 (ลิฟต์/ช่อง), G3 (หลายชั่วโมง–หลายวัน), สถานะงาน "กำลังทำ/เสร็จ/รับรถได้" |
| ถัดไป | ร้านอาหาร (คิวหน้าร้าน), ติวเตอร์/ฟิตเนส (คลาส capacity), ราชการ/ธนาคาร (ticket mode, ขายยาก ระยะยาว) | เมื่อ G2 + capacity พร้อม | |

### 6.5 วงจรการเติบโตที่ไม่ต้องซื้อโฆษณา [REC]
1. **ร้านสมัครเพราะฟรี + 10 นาที + ไม่ต้องมี OA** (เสา 2) — ช่องทาง: กลุ่ม LINE/Facebook เจ้าของร้านแต่ละ vertical, คอนเทนต์ SEO ต่อ vertical (MeQueue พิสูจน์ว่าได้ผล), เทมเพลตพร้อมใช้
2. **ร้านแปะ QR หน้าร้าน** (walk-in self-join) — ลูกค้าทุกคนที่เดินเข้าร้านสแกน = ได้ตัวตน Quego โดยไม่ต้องสมัคร → **นี่คือ viral loop ที่ booking tools ไม่มี** เพราะพวกเขาไม่รองรับ walk-in
3. **ลูกค้าที่มีตัวตนแล้วเห็น "ร้านใกล้ฉัน" ข้ามหมวด** → ร้านได้ลูกค้าใหม่จาก network → เหตุผลให้ร้านอยู่ต่อและบอกต่อ
4. **ร้านที่โต (หลายสาขา/หลายคน) จ่าย Pro** · **แพลตฟอร์มอื่นต่อ API** → รายได้มาจากคนที่ได้ประโยชน์มากสุด ไม่ใช่ร้านเดี่ยว

### 6.6 ความเสี่ยงของทาง horizontal (ต้องรู้ก่อนเลือก)
| ความเสี่ยง | ระดับ | วิธีลด |
|---|---|---|
| **ตื้นทุกที่ ลึกไม่มีที่ไหน** — vertical เจ้าถิ่นชนะด้วย integration (HIS, POS, บัญชี) | สูง | ไม่แข่งที่ integration แต่เป็น *engine ที่ integration มาต่อ* (API) และเลือก beachhead ที่ไม่มีเจ้าถิ่น |
| **Messaging "ทุกธุรกิจ" ทำให้ไม่มีใครรู้สึกว่าทำเพื่อเขา** (บทเรียนเดิมที่ repositioning "ทุกธุรกิจที่มีลูกค้าต่อคิว" ถูกพัก) | สูง | landing กลาง 1 หน้า + landing ต่อ vertical ที่ใช้คำของ vertical นั้น (คนไข้/ลูกค้า/รถ) บนเทมเพลตเดียวกัน |
| **LINE ลงมาทำเอง** | สูงสุด | ไม่พึ่ง LIFF/MINI App เป็นแกน; ทำให้ Quego มีค่าแม้ไม่มี LINE (web push, API, discovery) |
| **ต้นทุน LINE โตตามคิวแต่รายได้ 0 ในช่วงแรก** | กลาง | guardrail push/เดือน; web push เป็น fallback ฟรี; Pro tier เมื่อถึง 10,000 push/เดือน |
| **Network effect ไม่เกิดถ้า supply กระจุก** | กลาง | วัด "ลูกค้าที่ใช้ ≥ 2 ร้าน" เป็น KPI ตั้งแต่ร้านที่ 50 |

## 7. 90 วันแรกถ้าเลือกทางนี้ [REC]

| สัปดาห์ | ทำ | ผล |
|---|---|---|
| 1–2 | ปิดหนี้ที่ยังไงก็ต้องมี: reminder (N1), no_show (N2), export (N5), SEO (N3) | ร้านใดก็ใช้ได้โดยไม่รู้สึกว่าถูกหลอก; PDPA ผ่าน |
| 3–6 | **G1 resource + capacity**, **G3 เวลายืดหยุ่น**, **G5 industry templates** (นวด/สปา, คลินิก, บริการรถ) + landing ต่อ vertical | เปิดรับ 3 vertical ด้วยโค้ดชุดเดียว |
| 7–10 | **G2 โหมดคิว/นัด/hybrid**, display privacy mode, staff view (role แรก) | คลินิก + ร้านอาหารเริ่มได้; ร้านหลายคนใช้ได้จริง |
| 11–13 | **Public API v0 + webhooks + API keys** + เอกสาร | เริ่มคุยกับ POS/OA vendor; ทาง C เปิด |
| ตลอด | หาร้านจริง 30 ร้านใน 3 vertical ผ่านกลุ่ม LINE/Facebook + concierge onboarding; วัด "คิว/วัน" และ "ลูกค้าใช้ ≥ 2 ร้าน" | ข้อมูลจริงมาแทนสมมติฐาน |

**KPI เดียวที่บอกว่าทางนี้ถูก**: ภายใน 90 วัน มีร้านจริง ≥ 30 ร้านใน ≥ 3 ประเภทธุรกิจ รับคิวรวม ≥ 200 คิว/วัน โดยไม่ต้องซื้อโฆษณา — ถ้าไม่ถึง ปัญหาไม่ใช่ฟีเจอร์ แต่คือ distribution และต้องกลับมาคุยเรื่องช่องทางก่อนสร้างอะไรเพิ่ม

## 8. สรุปสำหรับตัดสินใจ

1. **ใช่ — ไป horizontal ได้ และควรไป** เพราะ engine เป็นกลางอยู่แล้ว 80% และสนาม "ระบบจองความงาม" แออัดเกินกว่าจะเป็นเบอร์ 1
2. **แต่ horizontal คือสถาปัตยกรรม ไม่ใช่การตลาด** — ขายทีละ vertical ด้วยเทมเพลตและภาษาของเขา เริ่มที่นวด/สปา → คลินิกเล็ก → บริการรถ
3. **จุดต่างที่แท้จริงมี 3 อย่าง**: hybrid race-safe engine · ร้านไม่ต้องมี OA/ไม่จ่ายค่าข้อความ · ตัวตนผู้บริโภคข้ามร้าน — อย่างที่ 3 คือ moat ระยะยาวและเป็นเหตุผลเดียวที่ต้องข้ามอุตสาหกรรม
4. **รายได้มาจากธุรกิจที่โต (Pro) และแพลตฟอร์มที่ต่อ API ไม่ใช่ร้านเดี่ยว ไม่ใช่คอมมิชชัน**
5. **ฟีเจอร์ใน review ฉบับก่อนไม่ได้ผิด แต่ผิดลำดับ**: มันคือ "ทำให้ร้านอยู่ต่อ" ซึ่งไร้ค่าจนกว่าจะมีร้าน — ลำดับที่ถูกคือ ปิดหนี้ 4 ข้อ → generalize engine → เทมเพลต 3 vertical → API → แล้วค่อย polish
