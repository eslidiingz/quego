## สรุปภาพรวม

พื้นฐานแข็งแรง: ไม่พบ IDOR ในฝั่งร้านและฝั่งลูกค้า (ทุก mutation ใช้ `id + shop_id/customer_phone`
จาก session), upload ตรวจ magic byte, LINE webhook ตรวจ HMAC บน raw body, OAuth state ผูก cookie,
lockout ใช้ compare-and-swap, scrypt + timingSafeEqual, ไม่มี secret ใน log

ปัญหาที่พบรวมกันอยู่ 3 กลุ่ม: (1) ช่องที่ "ไม่ต้องพิสูจน์ว่าเป็นเจ้าของเบอร์" (2) rate limit ที่ key ผิดหรือ
fail-open (3) dependency และ DB grant ที่ต้องอัปเดต

## Critical / High

### C1. ยึดร้านที่ยังไม่ตั้ง PIN ได้ด้วยแค่รู้เบอร์เจ้าของ — CONFIRMED
- `src/app/shop/login/pin/actions.ts` `setupShopPin` ตรวจแค่ login-intent cookie
- intent ออกให้ใครก็ได้ที่พิมพ์เบอร์ร้านใน `/login?tab=shop` (`src/app/shop/login/actions.ts`)
- ร้านถูกสร้างแบบ approved ก่อนมี PIN (`src/app/shops/register/actions.ts`)
- ฝั่งลูกค้าทำถูกแล้ว: `src/app/login/pin/actions.ts` บังคับ `isPhoneVerified(intent.phone)`
- ผลกระทบ: เจ้าของที่สมัครแล้วทิ้งหน้า PIN หรือแถวเก่าที่ `pin_hash IS NULL` ถูก login แทนได้เต็มสิทธิ์
- แก้: ใน `setupShopPin` บังคับ `isPhoneVerified(intent.phone)` แล้ว `clearPhoneVerified()` หลังสำเร็จ
  หรือใส่ claim `setupAllowed` ใน intent ที่ออกเฉพาะจาก registerShop หลัง OTP

### C2. Next.js 16.2.6 มี advisory critical 5 รายการ (RCE) — CONFIRMED
- `pnpm audit --prod`: 36 รายการ (5 critical, 17 high) เกือบทั้งหมดอยู่ใน `next` และ transitive ของมัน
- Critical ที่เกี่ยว: RCE ใน Image Optimization (AVIF/SVG), RCE ใน `next/og` ImageResponse, RCE ใน `use cache`
- โค้ดเราไม่ใช้ `next/image`, ไม่มี `remotePatterns`, ไม่มี `use cache`; `opengraph-image.tsx` เป็น static ไม่มี input
  → exposure จริงต่ำ แต่ `/_next/image` endpoint ยังเปิดอยู่โดย default
- แก้: อัปเกรด `next` และ `eslint-config-next` เป็น ≥16.4.1 (ปิดทุก advisory), `firebase` ตัวใหม่ (grpc-js)

### H1. จองคิว / waitlist / walk-in ได้โดยไม่พิสูจน์เบอร์ ไม่มี cap ต่อเบอร์หรือต่อร้าน — CONFIRMED
- `src/lib/services/bookings.ts` createBooking: เบอร์เป็น free text, cap เดียวคือ `book:${ip}` 10/10 นาที
- `src/lib/services/waitlist.ts` `waitlist:${ip}` 10/10 นาที; walk-in `walk-in:${shopId}:${ip}` 20/10 นาที
- ผลกระทบ: จองด้วยเบอร์คนอื่น → เหยื่อได้ LINE push + เห็น booking แปลกใน `/me/bookings`;
  1 IP จองได้ ~1,400 รายการ/วัน เติมปฏิทินร้านคู่แข่งได้; limiter fail-open ทำให้ cap หายเมื่อ DB สะดุด
- แก้: ถ้ามี customer session บังคับ `customer_phone = session.phone`; anonymous ต้องผ่าน OTP
  (reuse `isPhoneVerified`) หรืออย่างน้อย cap ต่อเบอร์ (เช่น 1 active booking/ร้าน/วัน, ≤3 open ต่อเบอร์)
  + bucket ต่อร้าน

### H2. เปลี่ยน PIN ของร้านและลูกค้าเป็น PIN oracle ไม่มี throttle — CONFIRMED
- `src/lib/services/customers.ts` `changeCustomerPin`, `src/lib/services/shops.ts` `changeShopPin`:
  `verifyPassword(currentPin, …)` ตรงๆ ไม่มี lockout ไม่มี rate limit
- action ที่เรียก (`src/app/me/profile/actions.ts`, `src/app/shop/(authed)/profile/actions.ts`) ก็ไม่มี
- admin ทำถูกแล้ว (`src/lib/services/admins.ts` ใช้ lockout ร่วม)
- ผลกระทบ: cookie ถูกขโมย 8 ชม. → เดา PIN ได้ไม่จำกัด → login ถาวรจากเครื่องอื่น
- แก้: เลียนแบบ `changeAdminPassword` (lockout CAS + `checkRateLimits` key ด้วย customerId/shopId)

## Medium

### M1. `/bookings/[id]` เดาเบอร์ได้ (limiter key รวม IP, mask เหลือ 5 หลักไม่รู้) — CONFIRMED
- `src/app/bookings/[id]/actions.ts`: bucket `booking-cancel:${bookingId}:${ip}` → หมุน IP ได้ budget ใหม่
  (comment ในไฟล์บอกตรงข้าม ซึ่งผิด)
- `page.tsx` แสดง `08X-XXX-XX99` → เหลือ 10^5 combos; cancel/reschedule ตอบ `not_found` แยกแยะได้
- แก้: key ด้วย bookingId อย่างเดียว + lockout ต่อ booking เมื่อผิดซ้ำ; โชว์ 2 หลักท้ายพอ;
  หรือใช้ signed token `?k=` ในลิงก์แทนการพิมพ์เบอร์

### M2. `rate_limit_hit` เป็น SECURITY DEFINER และ anon เรียกได้ผ่าน REST — CONFIRMED (live DB)
- `supabase/migrations/20260620000000_baseline_schema.sql:53` ไม่มี REVOKE; Supabase advisor lint 0028/0029
- bucket name เดาได้ (`custpin:phone:08…`, `adminlogin:phone:…`) → ใครมี publishable key ล็อกเหยื่อได้
  หรือยิง bucket สุ่มให้ `rate_limits` บวม (ตอนนี้ 692 แถว, 689 หมดอายุ, ไม่มีอะไรลบ)
- publishable key ยังไม่ได้ใช้ใน browser bundle เลย ทำให้ exposure ตอนนี้ต่ำ แต่แก้ถูก
- แก้ (migration ใหม่):
  `REVOKE EXECUTE ON FUNCTION public.rate_limit_hit(text,integer,integer), public.tg_bookings_set_updated_at(), public.tg_customers_set_updated_at() FROM PUBLIC, anon, authenticated;`
  + `SET search_path = ''` + จำกัด `length(p_bucket)` + pg_cron ลบแถวหมดอายุ

### M3. LINE group bind ใช้ substring match และ overwrite เงียบ ไม่มี unbind — CONFIRMED
- `src/lib/line/message-commands.ts:29` `GROUP_BIND_RE = /เชื่อมร้าน|เชื่อมต่อร้าน|\/bind/i`
- `src/lib/services/shop-line.ts` อัปเดต `line_group_id` ทันที ไม่ถามยืนยัน; ไม่มี UI ยกเลิก
- ผลกระทบ: ผู้ร้ายตั้งกลุ่มที่มี OA + เชิญเจ้าของ แล้วล่อให้พิมพ์ประโยคที่มีคำว่า "เชื่อมร้าน"
  → booking ใหม่ทุกรายการ (ชื่อลูกค้า บริการ เวลา) ไหลไปกลุ่มผู้ร้าย เจ้าของแก้ไม่ได้
- แก้: exact match หลัง trim; ถ้ามี group อยู่แล้วต้อง confirm ผ่าน postback; push แจ้งเจ้าของทุกครั้งที่ bind;
  เพิ่ม "ยกเลิกการเชื่อมกลุ่ม" ในหน้า notifications

### M4. Kiosk/display ใช้ owner session เต็มสิทธิ์ — CONFIRMED (design)

### M5. เปลี่ยนสถานะ booking ไม่มี transition guard — CONFIRMED

### M6. ร้านยิง LINE push / ปลูก booking ให้เบอร์ใครก็ได้ ไม่มี throttle — CONFIRMED

  cancel ก็ push อีกครั้ง; ไม่มี `checkRateLimit` ใน shop action ใดเลย

### M7. ไม่มี session revocation / rotation — CONFIRMED

  `stopImpersonation` แค่ลบ cookie, token ที่ copy ไว้ยังใช้ได้ถึงหมดอายุ
- แก้: เพิ่ม `pin_changed_at`/`credentials_version` แล้วเช็คใน `verify*SessionToken`; impersonation TTL ≤1 ชม.

### M8. Account enumeration ทั้งสองฝั่ง — CONFIRMED

### M9. Firebase OTP: ไม่มี cap ฝั่ง server, token ไม่เช็ค freshness, config จริงอยู่ใน `.env.example` — PLAUSIBLE

- แก้: App Check + +66-only region + SMS quota (console) ก่อน go-live; `maxTokenAge: "10m"` + เช็ค `auth_time`
  + `firebase.sign_in_provider === "phone"`; HTTP-referrer restriction ที่ key ใน GCP; เปลี่ยน `.env.example` เป็น placeholder
